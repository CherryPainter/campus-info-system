# 上线清单：v6.19.0 → v6.21.0（跨版本，2026-10-01）

> 面向生产机 `yuetang.cloud`（Ubuntu + Nginx + Gunicorn + MySQL + Redis）。
> 当前线上 **v6.19.0**，本次一次性跳到 **v6.21.0**（6.20.0 与 6.21.0 的内容一并上线）。
> 上线由用户手动推送；本清单只列「照做即可」的步骤与「必须先知道」的风险。

---

## 0. 一句话总览

这次不是「只换代码」，有 **4 件事必须做**，漏一件就会出问题：

1. **装新依赖** `nh3`（不装 → 公告/自定义推送正文写入会被 fail-closed 拒绝）。
2. **跑数据库迁移** `python init_db.py migrate`（补新表 `announcement_channels` 与多张表的新列）。
3. **手动补一个唯一约束** `uq_user_notif_ref`（`migrate` 不会建）
4. **小程序与后端同步上线**（接口有破坏性变更，老小程序电量列表会空）。

### 生产 `.env` 需确认/补齐的键（跨版本新增，务必人工过一遍）

线上 `.env` 是 v6.19.0 时代配的，这中间模板新增了 10 个键、并有 2 个键**语义变了**。
多数新键有代码默认值（不配也能跑），但下面这些必须人工确认：

**(1) 两个键语义变更 —— 旧值会静默失效（最危险）**

| 键 | 旧写法（v6.19 前） | 现在必须是 | 不改的后果 |
|---|---|---|---|
| `QWEATHER_LOCATION` | LocationID，如 `101040100` | **`经度,纬度`**，如 `106.55,29.56` | 代码 `split(",")` 取两段当经纬度，LocationID 解析不出 → **静默回落到重庆坐标**，预警定位全错 |
| `WEATHER_SCHEDULE_DAILY` | 旧名 `QWEATHER_SCHEDULE_DAILY` | `WEATHER_SCHEDULE_DAILY` | 代码只读新名 → 旧名改了不生效（默认同为 07:00，只有改成别的值才暴露） |

**(2) 必填、且没有可用的公共默认值**

`QWEATHER_API_HOST`：旧的公共域名已停服（`devapi.qweather.com` 2026-01-01 停、`api.qweather.com` / `geoapi.qweather.com` 2026-06-01 停），继续用会直接 **HTTP 403 Invalid Host**。必须是**账号专属**域名（和风控制台「设置」页，形如 `abc.def.qweatherapi.com`）。

**(3) 生产安全项 —— 建议本轮开启**

- `APP_ENV=production` 与 `FORCE_HTTPS=true` **必须成对**设置：只设 `APP_ENV=production` 而不设 `FORCE_HTTPS=true`，启动守卫会**直接拒绝启动**。
- 开 `FORCE_HTTPS` 的前置条件：Nginx 必须转发 `X-Forwarded-Proto: https`（后端靠 ProxyFix 解析它判断 is_secure）；缺这个头会导致 **301 死循环**。生产此前一直不敢置 true 正是因 ProxyFix 缺失，该问题已于 **2026-09-30 修复，现在可以开**。
- `REGION_BLOCK_EXCEPTIONS`：境外 IP 拦截默认开启（`ENABLE_FOREIGN_IP_BLOCK` 默认 true），建议把自己的出口 IP 填进白名单，防止误锁自己。

**(4) 已删除的死键（生产若还留着可删，无害）**：`JWXT_SAVE_LOG`、`JWXT_CAPTCHA_MODE`、`QWEATHER_LATITUDE`、`QWEATHER_LONGITUDE`（后两个从未被代码读取）。

**(5) 有默认值、可不配**：`MAX_CONTENT_LENGTH`(10MB)、`CSRF_ALLOWED_ORIGINS`(空)、`JWT_REFRESH_IDLE_EXPIRE`(259200)、`JWT_REFRESH_ABSOLUTE_EXPIRE`(2592000)、`IMAGE_SIGNED_URL_TTL`(21600)、`WEBHOOK_URL_ALLOWED_HOSTS`(空)。

### 3.1 唯一约束必须手动补（migrate 不会建）

`uq_user_notif_ref` 定义在模型的 `__table_args__` 里、类型是 `UniqueConstraint`，而 `migrate` 只处理 `Index` 对象，**不会**创建它。**执行前先检查**（生产若已存在就跳过，否则 `ALTER` 会报 `Duplicate key name`）：

```sql
-- 先查：有输出就说明已存在，不必再建
SHOW INDEX FROM user_notifications WHERE Key_name = 'uq_user_notif_ref';

-- 没有才执行
ALTER TABLE user_notifications
  ADD UNIQUE KEY uq_user_notif_ref (user_id, ref_type, ref_id);
```

（作用：同一用户同一业务对象（如某条公告）只留一条站内信，防止重复推送。）

### 3.2 旧课程数据修复（一次性脚本，共 6 个，分两类）

课程相关的一次性脚本**不止两个**，关键是分清「随代码上线」与「必须手动上传」：

**(A) 随代码部署 —— 服务器 `/opt/Push_System_Flask/app/cqie-course-timetable/` 下本来就有**

| 脚本 | 作用 | 生产注意 |
|---|---|---|
| `reimport_with_teacher.py` | 从已保存的 `course_table.html` 重建课表，用源 HTML 解析的教师映射补全教师，**软删全部未删课程 + 重新入库** | 读 `.env`（`load_dotenv` + `create_app`），可直接在生产跑；但会先软删现有课程，若那份 HTML 是旧学期数据会把库刷成旧数据，**执行前务必确认 HTML 是当前学期** |
| `rebuild_course_meta.py` | 依据 DB 已有学期重建 `course_meta.json`（该文件若只含 1 个学期，全量爬取会「假全量」） | **坑：`DB_CONFIG` 硬编码本地库**（`127.0.0.1` / `123456`），生产直接跑会连错库，**必须先改成读 `.env` / 生产连接参数** |

**(B) 不入库，需手动上传到 `/opt/Push_System_Flask/`**（都在本地 `技术总结/`，被 `.gitignore` 忽略，`git pull` 带不上）

| 脚本 | 作用 |
|---|---|
| `diagnose_courses.py` | **只读体检**（本轮新增）：规模 / 学期×来源分布 / 重复组 / `weeks` 空与单周 / 单节碎片 / 空 key，末尾直接给结论。**即使还没 `course_key` 列也能跑**，建议第一个跑 |
| `backfill_course_key.py` | 按模型真实算法回填 `course_key`（幂等可重跑） |
| `cleanup_courses.py` | 合并单节碎片 / 去重 / 学期名归一（执行前自动整表备份到 `courses_bak_<时间戳>`） |
| `_local_inspect.py` | 只读核查：重复分组、空 key、学期分布（`diagnose_courses.py` 的超集，二选一即可） |
| `_local_verify_key.py` | 只读校验：存储的 key 与模型实时算法是否一致 |
| `dev-scripts/ingest_semester291_to_20261.py` | 把已爬取的 `semester_291` 产物并入 DB 学期 20261（**硬编码本地绝对路径**，生产需改） |

推荐执行顺序（**在 `/opt/Push_System_Flask` 目录下**用 venv，`backfill_course_key.py` 依赖 `sys.path.insert(0, ".")`）：

```bash
cd /opt/Push_System_Flask
venv/bin/python diagnose_courses.py        # 0) 只读体检：先看清脏在哪、有多严重
venv/bin/python backfill_course_key.py     # 1) 回填 course_key（旧行 key 就位）
venv/bin/python cleanup_courses.py         # 2) 清洗碎片/重复/学期名（会先整表备份）
venv/bin/python _local_verify_key.py       # 3) 复核：0 空 key / 0 不一致
# 4) 再由管理端触发一次全学期重爬（见 3.3），这一步脚本替代不了
```

> 不跑也能自愈：后续全量爬取时，`course_key IS NULL` 的旧行会按身份兜底匹配并写入正确 key
> （`_find_existing_course`）。但**重复行**不会被自动清掉，建议至少跑一次 `cleanup_courses.py`。
> 注：设计文档里提到的 `cleanup_courses.sql` **在仓库中并不存在**（全仓无任何 `.sql` 文件），实际实现是 `.py`。

### 3.3 触发一次全学期重爬（覆盖真实的 weeks —— 脚本替代不了这一步）

线上 `weeks` 存的是「爬取发生在第几周」而不是「这门课真正上到哪些周」，**这一条只有重爬能修**（`cleanup_courses.py` 明确不改 `weeks`，因为它无法还原真实周次）。修复后的爬虫必须带 `--all-weeks`：定时任务已强制带上（`executors.run_spider`），也可从管理端手动触发一次整学期爬取。

这次重爬的入库行为（已核 `course_repository.py`）：

1. **主匹配** `(semester_id, course_key)`；
2. 主匹配不中 → **弱身份兜底**（`(学期, 课名, 星期, 教室, 教师)` 且节次一致）——该兜底**对 `course_key` 为 NULL 的旧行同样生效**，命中后顺手把存储的 key 纠正为当前值。所以「不跑回填脚本」也能自愈，只是先回填（主匹配命中）比走兜底更稳；
3. **对账软删**：仅当 `reconcile=True` **且** `data_source='full'` 时，把本批**未命中**的 full 行软删（`deleted_reason='stale_reconcile'`）。

**两个盲区必须知道**：

- **`daily` 源的重复行不会被对账清掉**（reconcile 只管 `full`）→ 这部分要靠 `cleanup_courses.py` 收尾；
- `admin` 源的手动课受保护，不会被软删。

> 实测参考：本地库（**already 清洗过**）仍有 17 行 `weeks` 为真单周 —— 说明清洗脚本确实动不了 `weeks`，线上只会更多。

## 7. 风险与注意

1. **别跳过 `pip install`**：`nh3` 缺失时正文读写会 fail-closed（拒绝），公告/自定义推送会直接报错。
2. **别只重启不迁移**：缺 `course_key` 列会让课程入库报错。
3. **Gunicorn 启动参数**：unit 必须是 `gunicorn -c gunicorn_config.py run:app`，
   不要写成 `gunicorn -w 4 run:app`（每个 worker 会各起一份 APScheduler，定时任务重复执行 N 倍）。
4. **`.env` 的 `HOST` 与 Gunicorn 无关**：生产监听地址由 `gunicorn_config.py` 的 `bind`（默认 `127.0.0.1:29528`）决定。
5. **域名口径**：确认 `ALLOWED_ORIGINS` 含 `https://yuetang.cloud`（本地 `.env` 曾误写 `yuetang.COM`，已修正）。
